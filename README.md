# 发票合并小助手

把多张发票 PDF 合并成一个文件，自动处理横向 / 纵向页面，保证每页方向正确、内容不被旋转或裁切。

适用场景：报销前把十几张电子发票、扫描件、拍照件合成一个 PDF 提交。

### 关于输出尺寸怎么选

只剩两个选项，按用途挑：

- **报销、归档、要贴票** → 用默认的**统一 A4 纵向（横向页旋转填满）**。整份纸面统一成 A4 纵向，
  横向内容整体旋转 90°（内容顶部朝右）后填满纸面，占的面积最大、打印最清楚；代价是横躺的文字
  要把纸逆时针转 90° 才能读，但全篇各页摆向一致，翻看不用来回换手。多数单位粘贴报销凭证就是这一种。
- **要求零损失、不做任何缩放** → 用**保持原始尺寸**。逐页按原始尺寸与方向输出，不重绘、不压缩，
  纵向页出纵向、横向页出横向。注意它只管"尺寸与方向"，和「输出为扫描件」是两回事：
  想连内容都不栅格化，还要把扫描件开关一并取消。

### 关于排序怎么选

- **报销材料** → 用**拼音顺序（中文习惯）**。中文材料按拼音先后排列，与资源管理器、多数国产办公软件一致；`dzfp_xxx.pdf` 这类英文开头的文件排在最后。这与人工整理报销材料的顺序基本相同。
- **发票按编号 / 日期排列** → 用**自然排序**，`发票2` 会正确排在 `发票10` 前面。
- 无论用哪种自动排序，都可以在界面上用**上移 / 下移 / 移到最前 / 移到末尾**手工微调成任意顺序。

### 材料分类规则

启用「整理报销顺序」后按下面的规则认材料，判断结果会打印在日志里、也写进报告，方便核对：

| 类别 | 识别依据（文件名与正文一起看） | 排序位置 |
| --- | --- | --- |
| 酒店发票 | 含 酒店 / 宾馆 / 旅店 / 旅馆 / 民宿 / 客房 / 住宿 / 入住 / 房费 / 饭店 | 第 1 位，两张缩放进同一页 |
| 差旅费报销单 | 含 差旅费报销单 / 差旅报销单 / 报销单 / 报销审批单 | 第 2 位 |
| 火车 / 飞机票据 | 含 机票 / 飞机票 / 航班 / 行程单 / 客票 / 火车 / 高铁 / 动车 / 铁路 / 12306 | 第 3 位，两张缩放进同一页 |
| 其他材料 | 上面都不匹配，以及 结账单 / 消费明细 / 登机凭证 / 登机牌 / 出差申请 | 第 4 位，三张一转进同一页 |
| 票据粘贴单封面 | 含 票据粘贴单 / 粘贴单 / 凭证封面 / 封面 | 最后 |

几点容易踩的地方：

- **结账单、电子登机凭证、出差申请审批单都归「其他材料」。** 它们只是随附的 A4 单据，
  不是税务发票或交通票据。结账单是酒店出具的消费流水；登机凭证虽带"登机"二字，
  但它是乘机时打印的整页纸，跟机票行程单不是一回事，所以"登机凭证 / 登机牌"
  会先于交通关键词命中。判定时会同时看文件名和正文，并排除带"发票"字样的文件，
  避免把"某某结账单发票"这类真发票误伤。
- **拼版是"缩放"，不是"裁切"。** 同一页上的每张材料都**完整**缩放后放进自己的条带，
  价税合计、备注、开票人这些关键信息都会保留。横向小票型发票（如 600×400 的电子发票）
  正文占满整页，缩放后字会小一些，但内容不缺。
- **哪些材料拼、拼几张。** 酒店发票和机票 / 火车票固定两张一页；其他材料三张一页，
  第四张起另起一页（落单的那份不缩小，独占整页）。差旅费报销单和票据粘贴单封面
  始终独占一页。不同类别不混排在同一张纸上。
- **其他材料里的竖版单据会转 90° 横躺。** 同样一份 A4 竖版单据，横着放进 1/3 条带
  比硬竖着塞大约成像一成半，所以两种摆法自动取大的那个，内容顶部朝右 ——
  与差旅费报销单、封面那套单页旋转的摆向完全一致。本来就是横版的材料不转。
- 相邻材料之间画一条裁切虚线，虚线上下各有 6 毫米空白，下剪子碰不到字。
- 关键词只是"够用就好"，不做语义理解。真被认错了，在界面上用手动排序调一下，
  或者关掉「小票拼版」开关即可。

## 四、工作原理

### 方向怎么判断

每页的显示方向由两部分合成：

1. **页面视觉尺寸**：`page.rect`，已经计入 PDF 的 `rotation` 属性。宽 > 高即横向。
2. **文字书写方向**：从文本层逐行取 `dir` 向量，按字符数投票，量化到 0° / 90° / 180° / 270°。

两者相加才是**肉眼看到的文字角度**。只有合成后仍不是 0°（水平）时才干预。这能同时处理两类常见异常：

| 异常 | 表现 | 处理 |
| --- | --- | --- |
| rotation 属性被误设 | 页面声明纵向、rotation=90，文字竖躺 | 把 rotation 改回 0 |
| 内容横躺 | 页面纵向，文字被逆时针转了 90° | 把 rotation 设为 90 |

判定采用保守策略：需要文本层，且某一方向占比 ≥ 60% 才动手。**纯图片的扫描件无法可靠判断旋转方向**（图像内部朝哪边只有 OCR 能知道），此时只提示、不擅自旋转。

### 为什么不会失真

- **保持原始尺寸模式**下，用 `insert_pdf` 逐页原样复制页面对象，不重新渲染、不重新压缩，矢量内容、文字层、原始图像质量全部保留。方向调整只改 `rotation` 属性，是不可逆无损操作。
- **统一尺寸模式**下，先把页面的旋转烘焙进内容，再按目标尺寸以 `keep_proportion=True` 居中缩放（contain）。宁可留白也不拉伸变形，更不裁切。

### 横向页旋转填满模式

选**统一 A4 纵向（横向页旋转填满）**时，横向页的处理是：

1. 读取该页文字的实际书写方向；
2. 计算出一个旋转角，让内容统一停在"文字角度 90°"的姿态 —— 也就是内容顶部朝右，看的时候把纸逆时针转 90°；
3. 把旋转烘焙进页面，再按 contain 方式放进 A4 纵向页。

这样横向材料在纵向纸上占的面积最大，打印最清晰。纵向材料完全不受影响，保持水平。

这里有个容易踩的坑：PDF 的 `rotation` 属性是**覆盖**语义而不是叠加，所以不能"在当前显示角度上再加 90°"，必须回到内容流的原始角度去反推目标值。程序里由 `portrait_target_rotation()` 统一处理，对两类常见输入都能算对：

| 源页形态 | 内容流角度 | 目标 rotation |
| --- | --- | --- |
| 声明纵向 + `rotation=90`（视觉横向） | 270° | 0（清除属性） |
| 声明横向、内容水平 | 0° | 270 |

### 内容被裁切怎么办

PDF 的 `CropBox` 定义了"显示窗口"。有些扫描件或 PDF 处理工具会把 `CropBox` 设得比内容小，导致发票边缘被切掉。

程序检测到内容紧贴页面边缘时，会比对内容实际范围与裁剪框，若确认超出就自动把 `CropBox` 扩回内容边界（且不超出 `MediaBox`），把被裁掉的部分找回来。

## 五、异常情况处理

| 异常 | 处理方式 |
| --- | --- |
| 文件不存在 / 不是文件 | 跳过，记入报告 |
| 扩展名不是 `.pdf` | 不收入待合并列表 |
| Office 临时文件（`~$` 开头）、隐藏文件 | 自动忽略 |
| 文件已加密、需要密码 | 先尝试空密码；失败则跳过并提示"需要密码"，不影响其他文件 |
| 文件损坏、不是合法 PDF | 捕获异常后跳过，记入报告 |
| 文档 0 页 | 跳过 |
| 单页处理失败 | 只跳过该页，其余页面继续写入 |
| 全部文件都不可用 | 明确报错，**不生成空文件** |
| 一页都写不进去 | 报错并放弃输出，避免产生 0 页 PDF |
| 输出文件已存在 | 自动追加 `(1)`、`(2)`，**绝不覆盖**已有文件 |
| 输出目录不存在 | 自动创建 |
| 输出写入失败 | 回退用另一组参数重试；仍失败则明确报错 |
| 保存后文件损坏 | 保存后回读校验页数，不一致则报错 |
| 合并过程中取消 | 已写入的临时结果丢弃，不产生半成品 |
| 报告文件写入失败 | 只提示，不影响已合并的 PDF |
| 图形界面启动失败 | 提示改用命令行模式 |
| 文件夹里混进了本工具上次的输出 | 按 `_合并_` / `发票合并_` / `_报告` 识别并排除，不会把上次的结果再合并一遍 |
| 系统里没有打印机 | 提示去「系统设置 → 打印机与扫描仪」添加，并询问是否改用预览程序手动打印 |
| `lp` 提交打印失败 | 原样弹出 `lp` 的报错信息，不吞掉 |
| 送打印后长时间没出纸 | 提交成功只说明任务已入队，会提示检查打印机电源 / 联机 / 纸张 |

合并结束后，跳过项、警告项、逐页处理动作都会写进 `xxx_报告.txt`。

### 打印没反应怎么排查

1. 确认系统认得打印机：苹果菜单 →「系统设置 → 打印机与扫描仪」，
   或命令行执行 `python invoice_merge.py --list-printers`。
2. 确认选对了打印机：工具里的「打印…」对话框会列出系统所有打印机，带「（默认）」的是默认机。
3. 看队列里有没有卡住的任务：终端执行 `lpstat -o`；要清空用 `cancel -a`。
4. 如果提示"已提交打印任务"却不出纸，通常是打印机本身的问题（关机、离线、缺纸、需要人工干预），
   与 PDF 生成无关。可以先用预览程序打开输出文件、按 ⌘P 打一张；能出纸就说明文件没问题。

### 重新打包 APP

改了源码之后想重新生成 app：

```bash
cd "/Users/beng003/Documents/正式工作/工具/发票合并小助手"
/Users/beng003/.workbuddy/binaries/python/envs/invoice-tool/bin/python -m PyInstaller \
  --noconfirm --clean \
  "build_app/发票合并小助手.spec" \
  --distpath "$PWD/dist_new"
```

打包完成后，把 `dist_new/发票合并小助手.app` 挪到工具目录即可。

打包要点（踩过的坑，记下来免得重来）：

- **必须用 3.12 那个解释器**（`envs/invoice-tool`）。managed 的 3.13.12 缺 Tcl/Tk 资源，
  打出来的 app 一开窗口就报 `Cannot find a usable init.tcl`。
- 用 `--windowed` 才会生成 `.app`；Tcl/Tk 数据由 PyInstaller 自动收集到
  `Contents/Frameworks/` 下的 `_tcl_data`、`_tk_data`，不用手工 `--add-data`。
- `--specpath` 会改变 spec 内相对路径的基准，所以**图标等路径一律写绝对路径**，
  否则会拼成 `build_app/build_app/AppIcon.icns` 而报找不到文件。
- 打包会先删除同名输出目录，若被系统的批量删除保护拦下，COLLECT 阶段会中断、
  产出一个空的 `.app` 骨架。换成全新的 `--distpath` 目录即可绕开。
- app 是 ad-hoc 签名的，内部依赖用相对链接，**整体拷贝到别的机器照样能跑**（已验证）。
- **装了 PySide6 才会打进去**：`pip install -i https://pypi.tuna.tsinghua.edu.cn/simple PySide6-Essentials`
  （直连 PyPI 会非常慢，实测 110MB 的包走镜像 20 秒、直连 20 分钟还没完）。
- 图标通过 `spec` 的 `datas` 打进去（`assets/` → `Contents/Resources/assets/`）。
  换了图标或加了新图标，要重新打包才生效。
- 加了 PySide6 后体积从 86 MB 涨到约 145 MB，多出来的基本都是 Qt 的库和插件。

### 打包 Windows exe

PyInstaller 不支持跨平台编译，Windows exe 由 GitHub Actions 在 `windows-latest` 上构建：

- 工作流：`.github/workflows/build_windows.yml`（推送到 main 自动触发，也可在 Actions 页手动触发）。
- 打包配置：`build_app/InvoiceMerge-win.spec`（onedir、窗口模式，图标 `build_app/AppIcon.ico`）。
- 产物：构建页的工件 `InvoiceMerge_Windows.zip`，解压后双击 `发票合并小助手.exe` 运行；
  整个文件夹可单独拷走（绿色版，不需要安装任何依赖）。
- 首次运行若被 SmartScreen 拦下，点「更多信息 → 仍要运行」，只需一次。
- 注意：`.gitignore` 里排除构建产物的规则要写成 `/build/` 这种根锚定形式，
  写成 `build*/` 会把 `build_app/`（spec 与图标）一并排除，导致 CI 找不到 spec。

## 八、已知限制

1. **纯图片扫描件的方向纠正**：无文本层时无法确定该往哪边转，程序只给提示，需要人工确认或预先用扫描软件转正。
2. **独立页面的尺寸差异**：保持原始尺寸模式下，输出 PDF 各页尺寸可能不同（这是符合 PDF 规范的正常现象，所有阅读器都能正确显示）。需要版式完全一致时请选统一尺寸模式。
3. **不识别发票内容**：程序只做页面几何层面的合并与方向处理，不解析发票金额、抬头，也不做去重。
